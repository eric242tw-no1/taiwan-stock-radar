# C. 模型調度與動態升降級守則

適用對象：主對話模型（任何等級）。目的：主對話 context 保持乾淨、驗證與實作隔離、錯誤不無限重試。

## 1. 角色定義與「指揮官不下場」量化門檻

**指揮官（主對話）只做**：理解需求、拆任務、派工、讀 subagent 的精簡回報、做決策、向 User 報告。
**工兵（subagent）做**：大量讀檔、repo 掃描、實作、跑測試、驗收。

指揮官必須派工（而不是自己動手）的量化門檻——滿足任一條就派：

| 條件 | 門檻 | 派給 |
|---|---|---|
| 要開的檔案數 | > 5 個 | Explore agent（搜尋）或 general-purpose |
| 單檔要讀的行數 | > 400 行且只為了找某段邏輯 | Explore agent（回報路徑:行號即可） |
| 要跨的目錄數 | > 2 個目錄的搜尋 | Explore agent |
| 實作改動範圍 | > 2 個檔案**或** > 30 行 diff 的實作 | general-purpose（用 E 模板 2） |
| 驗收 | 預設派（豁免條件見第 4 節末） | fresh-context verifier（用 E 模板 4） |

指揮官**可以**自己做的：讀單一已知路徑的檔案（≤ 400 行）、小修（≤ 2 檔**且** ≤ 30 行 diff）、跑單條驗證指令。兩表互補無縫：超出「可自做」上限即落入派工門檻，不存在中間帶。

**回報紀律**：subagent 的最終回報進主對話。派工時必須用 E 模板規定回報格式——成果路徑 + 關鍵行號 + 結論，**禁止大段代碼**（> 15 行的代碼引用一律改為 路徑:行號）。

## 2. 派工三件套（缺一件 = 不合格的派工，重寫 prompt）

每次 Agent 呼叫的 prompt 必含：

1. **明確目標與背景**：一句話目標 + 為什麼做 + 已知的相關事實（檔案路徑、已確認的結論）。subagent 是冷啟動，對話裡的共識它全都不知道，必須寫進 prompt。
2. **嚴格驗收條件**：可執行的指令 + 預期輸出（例：`docker exec taiwan-stock-radar-fastapi-1 python -m pytest tests/test_market_router.py -q` 全綠）。「確保功能正常」不是驗收條件。
3. **標準回報格式**：明列回報要有哪些欄位（見第 5 節），並寫明「禁止貼超過 15 行的代碼」。

模板直接抄 [E-dispatch-templates.md](E-dispatch-templates.md)。

## 3. 異常升降級路徑

模型階梯（便宜→貴）：Haiku → Sonnet → Opus 4.8。Agent 呼叫用 `model` 參數指定，合法值只有小寫的 `haiku` / `sonnet` / `opus`（不要寫 `opus-4.8` 之類版本號，會報錯）。

| 情境 | 動作 |
|---|---|
| Haiku 出現 1 次工具調用錯誤或語法錯誤 | 立即改派 Sonnet 重做整個子任務（不要讓 Haiku 重試） |
| Sonnet 同一子任務連續失敗 2 次 | 升級 Opus 4.8，prompt 必須帶上**完整失敗軌跡**：兩次各自改了什麼、跑了什麼指令、完整錯誤輸出。禁止只寫「Sonnet 失敗了請處理」 |
| Opus 解出了固定模式（如：一種修法要套用到 N 個檔案） | 把已驗證的模式寫成明確步驟，降回 Sonnet/Haiku 批次套用，每批完成後仍走隔離驗證 |
| 同一件事已重試 2 輪仍失敗 | **禁止第 3 輪**。停下，走 [D-judgment-checklist.md](D-judgment-checklist.md) 第 1 節判斷是否方向錯誤，或第 3 節熔斷提問 |

「同一子任務」的判定：目標相同就算同一任務，換個寫法再試仍計入重試次數。

Haiku 適用範圍（超出就直接用 Sonnet）：機械性批次套用已驗證的模式、格式轉換、單檔摘要。**Haiku 不得做**：debug、多檔實作、任何驗收。

## 4. 隔離驗證（實作者不得自驗）

規則：**寫代碼的 agent 說「完成」不算完成**。它的自測結果只是參考。

驗收必須由 fresh-context subagent 執行（新的 Agent 呼叫，不是 SendMessage 給原實作 agent），驗收動作從下面選至少兩項：

1. **Read-back**：重新讀改動後的檔案，核對是否符合需求描述（不是核對是否符合實作者的回報）。
2. **實跑測試**：`python -m pytest tests/ -q`（容器內）或針對性的測試檔；前端用 preview 工具實際載入頁面。
3. **實打端點**：`curl http://localhost:8000/api/...` 核對狀態碼與關鍵欄位。
4. **多樣本評審**：僅用於高風險改動（風控/下單邏輯）——派 2 個獨立 verifier，結論不一致時升級問 User。

驗收 prompt 用 E 模板 4，且**不要告訴 verifier 實作者的結論**，只給需求與驗收條件（避免確認偏誤）。

小改動豁免：≤ 2 檔且 ≤ 30 行 diff 且不涉風控/下單/資料寫入 → 指揮官可自行跑驗收指令代替派 verifier，但指令必須實跑，輸出必須貼進回報。

## 5. 標準回報格式（subagent 回報必含欄位）

```
【結論】一句話：完成/失敗/部分完成 + 最重要的一個事實
【改動/發現】路徑:行號 清單，每項一行說明（禁止大段代碼）
【驗證】實際執行的指令 + 實際輸出（原文貼關鍵行）
【未解決/風險】沒有就寫「無」，不許省略此欄
```

指揮官收到回報後的義務：檢查【驗證】欄是不是真的有指令輸出。只有描述沒有輸出 → 退回重做，不得採信。
