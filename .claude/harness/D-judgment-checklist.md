# D. 判斷力外化矩陣

用途：把「該停了」「這才算完成」「該問人了」的直覺變成可肉眼比對的條件。
比對方式：逐條檢查，命中任一條就執行對應動作，不需要「綜合判斷」。

## 1. 換路徑信號：立刻停下，不要原地重試

命中任一條 → 停止當前修法，回到上一個乾淨狀態（`git diff` 檢視、必要時 `git stash`），重新讀需求與相關代碼，換一條路徑。連續命中兩條 → 直接走第 3 節熔斷提問。

| # | 信號 | 完美正例（該做的） | 典型反例（弱模型常犯） |
|---|---|---|---|
| 1-1 | 同一個症狀已用 2 種不同修法修過仍存在 | 停手。宣告「兩次修復無效，症狀不變，我對根因的假設可能錯了」，回頭重新收集證據（log、實際請求、DB 狀態） | 第 3 種修法再試一次，「這次應該可以」 |
| 1-2 | 每次修復 diff 越來越大，但症狀不變或轉移 | 「diff 已從 10 行膨脹到 80 行且症狀轉移，我在錯的層級修。revert，換層級找根因」 | 繼續在 80 行上疊第 81 行 |
| 1-3 | 開始需要改框架/庫/工具本身的行為來遷就自己的代碼 | 「我在對抗 Next.js 的代理行為，這通常代表用法錯了。查 pitfalls.md 和 skill 文件有沒有既定做法」（本專案 SSE 直連就是這類既定解） | 給框架打 patch、加 hack flag 硬繞 |
| 1-4 | 測試需要越來越多 mock 才能通過 | 「這個測試要 mock 4 個依賴才能跑，說明設計或測法錯了」，改測公開行為或調整切面 | 再 mock 第 5 個 |
| 1-5 | 蹺蹺板：修 A 壞 B、修 B 壞 A | 停。兩個症狀有共同根因，往上一層找（通常是共享狀態或順序假設） | 在 A、B 之間來回打補丁 |
| 1-6 | 為了讓錯誤消失而刪測試、放寬斷言、加 try/except 吞例外 | 這不是修復。錯誤訊息是證據，保留它，找根因 | `except Exception: pass` 然後宣告修好了 |

## 2. 完成定義（Definition of Done）：什麼叫「真正完成」

原則：**每一項驗收都是「可貼上執行的指令 + 預期輸出」**。寫不出指令的驗收條件不算驗收條件。
「code 寫完了」「測試理論上會過」「邏輯上正確」都不是完成。

按任務類型的最低驗收門檻（全部滿足才可宣告完成）：

**後端改動**
1. 相關 pytest 綠：`docker exec taiwan-stock-radar-fastapi-1 python -m pytest tests/ -q` → 預期 `0 failed`（至少跑受影響的測試檔）
2. 實打端點：`curl -s http://localhost:8000/api/<受影響端點>` → 200 且關鍵欄位有值（寫出具體欄位名）
3. 無新錯誤：`docker logs taiwan-stock-radar-fastapi-1 --tail 30` → 沒有本次改動引入的 ERROR/Traceback

**前端改動**
1. Preview 實際載入：`preview_start({name:"frontend"})` → snapshot 看到預期文字/元素（寫出具體要看到什麼）
2. Console 無紅字：preview_console_logs level=error → 無本次改動引入的錯誤
3. 資料真的來了：改動頁面顯示實際資料而非空狀態/skeleton（SSE 頁面例外：preview 驗不了 SSE，改用 `curl -sN http://localhost:8000/api/stream/...` 直連驗證，見 skill dev-env）

**資料管線改動**
1. 筆數前後對比：跑 `SELECT COUNT(*)` 於目標表，前後數字都寫進回報
2. 抽 1 筆驗值：SELECT 一筆實際資料，肉眼核對欄位值合理（日期格式、數字範圍）
3. 排程不壞：`curl -s http://localhost:8000/api/health` 回 200，且 `docker logs taiwan-stock-radar-fastapi-1 --tail 30` 無排程相關錯誤

**完美正例**：「已完成。驗證：pytest 13 passed；curl /api/market/indicators/2330 回 200，rsi=62.3 非 null；docker logs 無新 ERROR。」
**典型反例**：「已完成指標計算功能，代碼邏輯正確，測試應該可以通過。」（零指令、零輸出 → 這是「未完成」的同義詞）

## 3. 熔斷提問：何時停止自主作業問 User

命中任一條 → 停止該方向的自主作業，用 AskUserQuestion 或在回覆末尾列選項。其餘不相關的工作可以繼續。

| # | 條件 | 說明 |
|---|---|---|
| 3-1 | 觸碰風控紅線數值、下單邏輯、任何會動到真錢/真單的路徑 | 無條件問，包括「只是重構沒改行為」的情況 |
| 3-2 | 要刪除/覆蓋不是自己建立的檔案，且其內容與任務描述不符 | 先呈報發現，不動手 |
| 3-3 | 需求存在 ≥ 2 種合理解讀，且選錯的重工成本 > 30 分鐘 | 列出解讀讓 User 選；成本小就選最保守解讀繼續，回報時標註 |
| 3-4 | frontend/app/stock/page.tsx 有未提交變更且任務要動它 | User 手調版面，先問 |
| 3-5 | 動作有外部不可逆後果：打有封鎖風險的 API（TWSE MIS 超頻）、花錢、對外發布 | 先問 |
| 3-6 | 第 1 節信號連續命中 2 條 | 帶著證據問：「兩條路都失敗，軌跡如下，需要你決定方向」 |
| 3-7 | 品味/美感/文案決策 | 出 2–3 選項 + 截圖 + trade-off，不自作主張（見 A 誠實條款） |

**完美正例**：「發現 stop-loss 計算要動到 2% 上限的判斷式。這是風控紅線，我先停在這裡。選項 A：… 選項 B：…」
**典型反例**：「順手把停損邏輯重構了一下，行為應該不變。」

## 4. Context 熔斷：session 快滿時的收尾程序

觸發信號（任一）：系統提示 context 即將壓縮/已壓縮；或自覺已進行超長多檔任務、開始忘記早期指令。

收尾程序（順序執行，不可跳過）：
1. 停止接新工作，完成手上這一個原子步驟（寫到檔案為止）
2. 把未完成項目與當前狀態寫進交接處：任務進行中 → 寫入該 openspec change 的 tasks 或 `harness/G-handover.md` 末節；踩到的坑 → pitfalls.md
3. 跑一次 `git status` 把狀態寫進交接，讓下個 session 知道工作樹哪些是本次改的
4. 在主對話輸出一頁摘要：做完什麼、沒做完什麼、下一步第一件事是什麼
